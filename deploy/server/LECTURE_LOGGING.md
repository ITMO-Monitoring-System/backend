# Логи одной лекции: порядок работы на новом сервере

Это локальная реализация. Пока серверные файлы не установлены и контейнеры не
пересозданы с драйвером `journald`, команды ниже на сервере не заработают.
После установки службы и пересоздания `face_tracking` запись включается и
выключается кнопками лекции. Отдельные команды нужны только для диагностики.

## Подготовка сервера вне лекции

1. Проверить действующие настройки: `systemd-analyze cat-config systemd/journald.conf`,
   `journalctl --disk-usage`, `df -h /`, `timedatectl status`,
   `docker inspect --format '{{.HostConfig.LogConfig.Type}}' $(docker ps -q --filter label=com.docker.compose.project=itmo-monitoring)`.
   Не выводить `docker inspect` целиком: в нём есть переменные с паролями.
2. Настроить постоянное хранение и лимиты журнала по
   `journald/itmo-monitoring.conf.example`, сверив их с настройками хоста.
   Файл влияет на весь сервер; перезапуск `systemd-journald` планировать отдельно.
3. Доставить `deploy/server/` на сервер. На существующем хосте выполнить
   `sudo bash upgrade-lecture-logging.sh` из доставленного каталога. Скрипт
   сохраняет прежние `compose.yaml` и `nginx.conf`, устанавливает сборщик и
   останавливает активный `itmo-update.timer` до конца работ. Для новой установки подходит
   `install-server.sh`.
4. Вне лекции выпустить новый релиз через `manage.py deploy` с текущим
   `/opt/itmo-monitoring/deploy/current/release.json`; это применит настройки
   `journald` к пересозданным контейнерам. Проверить `manage.py check`,
   `systemctl is-active itmo-lecture-logs.service`, наличие сокета
   `/opt/itmo-monitoring/lecture-log-control/control.sock` и тестового события
   `CONTAINER_TAG=itmo-monitoring/backend` в `journalctl -o json --all`.
   После успешной проверки вернуть таймер, если он был активен до установки:
   `sudo systemctl start itmo-update.timer`.

Участник группы `systemd-journal` читает системный журнал хоста шире, чем
журналы этого проекта. Каталог архивов принадлежит `itmo-deploy` с правами
`0700`; файлы создаются с правами `0600`.

## Оператор лекции

Нажать «Начать лекцию» в интерфейсе. `face_tracking` сначала запрашивает у
сборщика новый архив, затем запускает очередь и распознавание. Если сборщик
недоступен, лекция не стартует и интерфейс показывает ошибку. Повторный запрос
во время той же лекции возвращает тот же `session_id`.

Нажать «Остановить лекцию». `face_tracking` завершает очередь и сообщает
сборщику время окончания. Архив ещё 60 секунд собирает события завершения,
после чего формируются файлы и контрольные суммы. Если сообщение о завершении
не дошло, интерфейс показывает ошибку и позволяет повторить остановку. При
следующем запуске той же лекции создаётся отдельная папка; готовый архив
предыдущего запуска не перезаписывается.

Для диагностики на сервере:

```bash
sudo -H -u itmo-deploy python3 /opt/itmo-monitoring/deploy/lecture_logs.py status
```

Проверять `status` до состояния
`completed` или `partial`. `partial` означает известный пропуск; посмотреть
`known_gaps` и `warnings` в `manifest.json`. Если остановка не была записана,
выполнить `recover --session-id ID_ИЗ_START`: такой архив будет помечен как
частичный. Ручные `start` и `stop` остаются для аварийных случаев.

После готовности проверить целостность:

```bash
sudo -H -u itmo-deploy python3 /opt/itmo-monitoring/deploy/lecture_logs.py \
  verify --path /opt/itmo-monitoring/lecture-logs/ИМЯ_ПАПКИ
```

Копировать нужно всю папку целиком. После копирования запустить `verify` на
другом компьютере с тем же `lecture_logs.py`; JSON-конфиг для проверки сумм
не нужен. `verify` проверяет только папку и не обращается к серверу.
Дополнительные браузерные журналы и логи внешнего прокси помещать отдельно:
они не входят в исходные контрольные суммы.

## Границы проверки

Локальные тесты проверяют управление через сокет, повторный запуск той же
лекции без изменения старого архива, экспорт, точный `lecture_id`,
восстановление, маскирование секретов и контрольные суммы. На Linux-хосте
перед реальной лекцией ещё нужны пробный архив, рестарт сборщика, пересоздание
контейнера, проверка journald после ротации и измерение объёма/задержки под
нагрузкой. Браузерные ошибки и внешний прокси в этот архив не поступают.
